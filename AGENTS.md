# AGENTS.md

> Context file for AI coding assistants. Symlinked as `CLAUDE.md`.

## What this project is

Zerodep is a **zero-dependency, single-file Python module library**. Each module
lives in its own directory, uses only stdlib, and is designed to be copied
directly into projects via the `zerodep` CLI. Modules cover networking, serialization,
validation, text processing, agent protocols, and more — 40+ modules total.

Project versioning uses **CalVer** (`YYYY.M.D`); individual modules use **SemVer**.

## Repository layout

```
zerodep.py              CLI entry point (stdlib only)
manifest.json           Auto-generated module registry (DO NOT EDIT)
pyproject.toml          Project metadata, tool configs (ruff, ty, complexipy)
Makefile                40+ test/benchmark/lint/docs targets
.pre-commit-config.yaml Hooks: ruff, ty, complexipy
.github/workflows/      lint-test (reusable), CI, release, benchmark, PyPI
_scripts/               Doc generation utilities
docs_en/                ← git worktree (docs-en branch); English MkDocs site
docs_zh/                ← git worktree (docs-zh branch); Chinese MkDocs site
<module>/               Each module directory (45+)
  ├── <module>.py                   Implementation (single file, stdlib only)
  ├── test_<module>_correctness.py  Tests against reference library
  ├── test_<module>_benchmark.py    Performance benchmarks
  └── conftest.py                   Optional fixtures
```

## Setup

```bash
# Activate the conda environment
conda activate zerodep

# Install in dev mode with test dependencies
pip install -e ".[dev]"

# Install pre-commit hooks
pre-commit install
```

Run `make help` for all available targets.

## Key commands

All module operations go through the `zerodep` CLI — do not replicate their behavior manually.

```bash
# Module management
zerodep list                     # List all modules by category
zerodep info <module>            # Show module metadata (version, deps, tier)
zerodep new <name> --category <cat> --tier <tier>  # Scaffold new module
zerodep add <module> [module...] # Copy module files to target directory
zerodep update <module>          # Update existing module files

# Version & release
zerodep bump [modules...]        # Bump module versions (--patch|--minor|--major)
zerodep version-check            # Detect modules modified since declared version
zerodep version-check --strict   # Same, but exit 1 if any need bumping

# Manifest & dependencies
zerodep manifest                 # Regenerate manifest.json from source
zerodep dep-graph [module]       # Show dependency graph
zerodep dep-check [modules...]   # Test changed modules + downstream dependents
```

### Makefile shortcuts

```bash
make test                  # All correctness tests
make test-<module>         # Single module correctness test
make benchmark             # All benchmarks
make benchmark-<module>    # Single module benchmark
make lint                  # ruff check

make version-check         # Detect uncommitted version bumps

make dep-check             # Test changed modules + dependents

```

## Module structure

### Frontmatter

Each module file starts with a PEP 723-style metadata block:

```python
# /// zerodep
# version = "0.3.1"
# deps = ["httpclient"]
# tier = "subsystem"
# category = "serialization"
# ///
```

- **version**: SemVer — bumped via `zerodep bump`, never edit manually
- **deps**: inter-module dependencies — must match actual imports
- **tier**: `simple`, `medium`, or `subsystem`
- **category**: one of `network`, `protocol`, `serialization`, `validation`, `text`, `config`, `terminal`, `crypto`, `image`, `process`, `storage`, `devtools`

## Non-obvious rules

- **No third-party imports** in module source files. Only Python stdlib. Test files may import reference libraries for comparison.
- **Do not edit `manifest.json`** — it is auto-generated by `zerodep manifest`. After changing any module metadata, run `make manifest`.
- **Do not manually edit version in frontmatter** — use `zerodep bump`. It tracks content hashes to detect actual changes and prevent double-bumping.
- **Inter-module deps must be declared** in the `deps` frontmatter field. Undeclared cross-module imports will break `zerodep add` dependency resolution.
- **After creating a new module** with `zerodep new`, you must run `make manifest` and `make docs-index` to register it.
- **Pre-commit hooks must be installed** before making any commits. Run `pre-commit install` after cloning. The hooks run `ruff check`, `ruff format`, `ty check`, and `complexipy` automatically on commit — if a hook fails, the commit is blocked. Do not use `--no-verify` to bypass them.

## Testing

- Correctness tests compare zerodep output against reference libraries (PyYAML, httpx, pydantic, etc.)
- Benchmarks use `pytest-benchmark` for performance comparison
- Run `make dep-check` after modifying a module to ensure downstream dependents still pass

## Definition of done

1. `make lint` exits 0
2. `make test` passes (or at minimum `make test-<module>` for the changed module)
3. `pre-commit run --all-files` passes
4. New code has tests in `<module>/test_<module>_correctness.py`
5. Google-style docstrings on public APIs; comments in English
6. Module version bumped via `zerodep bump` if source changed
7. `make manifest` and `make docs-index` run after metadata or module changes

## Workflow

- **Branch from master**, open a PR, require CI green before merge.
- **Merge strategy: rebase merge** — every commit lands individually on master,
  so keep commits atomic and well-messaged.
- Branch naming: `feature/xxx`, `fix/xxx`, `docs/xxx`, `refactor/xxx`, `test/xxx`.
- PRs should describe *why* in the body, not just *what*.
- Never force-push to `master`.
- **No AI co-author tags in commits.** Do not add `Co-authored-by` lines for AI
  tools in git commit messages. Disclose AI usage in PR descriptions instead.

## Documentation

User-facing docs are bilingual, living on **orphan branches** mounted as
**persistent worktrees**:

```
docs_en/   ← docs_en branch (English, zensical)
docs_zh/   ← docs_zh branch (Chinese)
```

Edit docs files under `docs_en/docs/` or `docs_zh/docs/`, commit and push
inside the respective worktree. After adding or renaming modules, run
`make docs-index` to regenerate the module index pages.

### When to update docs worktrees

Update `docs_en/` and `docs_zh/` whenever any of the following happens:

- **New module added**: add the module to `_scripts/module_index_config.yaml`
  (both the `categories` list and the `modules` metadata section), then run
  `make docs-index` to regenerate `docs/modules/index.md` in both worktrees.
- **Module removed or renamed**: update `module_index_config.yaml` accordingly,
  then `make docs-index`.
- **Changelog-worthy change merged to master**: update
  `docs_en/docs/changelog.md` and `docs_zh/docs/changelog.md` under the
  `[Unreleased]` section. Follow the [Keep a Changelog](https://keepachangelog.com/)
  format. Changelog entries should cover: new modules, features, enhancements,
  bug fixes, performance optimizations, breaking changes, and infrastructure.
- **Release published**: move `[Unreleased]` entries into a new versioned
  section (CalVer `[YYYY.M.D]`) in both changelogs.

### Cross-language consistency (enforced)

**Both language versions must be updated in the same task/agent run.** Never
update only one language and leave the other for later. The workflow is:

1. Make changes to `docs_en/` first (English is the source of truth).
2. In the same task, apply equivalent changes to `docs_zh/` before committing.
3. Commit and push both worktrees before the task is considered done.

Splitting the two languages across separate agents or separate sessions is not
allowed — it leads to drift and missed pages.

Commits in doc worktrees use `PRE_COMMIT_ALLOW_NO_CONFIG=1 git commit` since
those branches have no `.pre-commit-config.yaml`.

## Release process

Releases use **CalVer** (`YYYY.M.D`). The process is mostly automated via
GitHub Actions:

1. **Ensure all changes are merged to master** and CI is green.
2. **Update changelogs** in `docs_en/docs/changelog.md` and
   `docs_zh/docs/changelog.md` — move `[Unreleased]` entries into a new
   versioned section `[YYYY.M.D]`.  Commit and push in both doc worktrees.
3. **Trigger the Release workflow** (`Actions → Release → Run workflow`).
   It auto-detects the CalVer version, bumps module versions, tags, and
   creates a GitHub Release with auto-generated notes.
4. **Rewrite the release notes** on GitHub if the auto-generated notes are
   insufficient — add structured sections (New Modules, Features, Bug Fixes,
   etc.).
5. The **Benchmark workflow** runs automatically on release publish.
6. The **PyPI workflow** runs automatically on release publish, but only
   publishes if `zerodep.py` or `pyproject.toml` have substantive changes
   (not just version bumps).

### CI architecture

Lint and test logic lives in a single **reusable workflow**
(`lint-test.yml`, triggered via `workflow_call`). Both `ci.yml` and
`release.yml` call it — no duplicated job definitions.

- **Lint job**: runs `pre-commit run --all-files` (ruff, ruff-format, ty,
  complexipy) — same hooks as local development.
- **Test job**: matrix across Python versions, dynamically installs
  `bench-*` reference libraries from `pyproject.toml`.
- `ci.yml` calls `lint-test.yml` with the default 4-version matrix.
- `release.yml` calls `lint-test.yml` with `["3.12"]` only as a quality
  gate, then runs release-specific steps.
- Benchmark and PyPI workflows are cascade-triggered on `release: published`
  and are independent.

### Reference library management

CI, release, and benchmark workflows all install reference libraries from
`pyproject.toml` `bench-*` extras dynamically. When adding a new module
with a reference library:

1. Add a `bench-<module>` extra in `pyproject.toml`.
2. Add it to the `dev` extra's dependency list.
3. No workflow YAML changes needed — the dynamic extraction picks it up
   automatically.

Exception: `bench-toon` is installed from git (not PyPI) and is handled
separately in each workflow.

## Escalation

- **Test failure**: check correct conda env is activated (`conda activate zerodep`)
- **`zerodep bump` says "no modules found"**: run via `conda run -n zerodep` or `python -m zerodep bump`
- **Pre-commit hook fails on `ty` or `complexipy`**: run commit inside conda env (`conda run -n zerodep git commit ...`)
- **Manifest out of date**: run `make manifest` — never edit `manifest.json` by hand
- **Test failure after 3 attempts**: stop, report full output — do not skip tests
- **Network issues**: try direct access first, use `proxychains -q` if needed

## Boundaries

### Allowed without asking
- Read files, run tests, run lint/format
- Run `zerodep info`, `zerodep list`, `zerodep dep-graph`

### Ask first
- Adding new inter-module dependencies (modifying `deps` in frontmatter)
- Deleting or renaming modules
- Modifying CI workflows or release configuration

### Never
- Import third-party packages in module source files
- Manually edit `manifest.json`
- Force push to master
