# Sibling Import 取舍分析

## 目的

这份文档专门回答一个核心问题：

> 既然我们已经判断 sibling import 不是理想设计，为什么第一轮改动只是统一写法，而不是直接删除？

这个问题非常关键，因为它触碰的不是某一段 import 代码，而是整个 `zerodep` 的产品承诺与架构边界。

相关背景文档：

- `plans/01-implementation-analysis-overview.md:1`
- `plans/02-refactor-roadmap.md:1`
- `plans/03-pattern-inventory.md:1`

相关实现位置：

- `config/config.py:33`
- `sse/sse.py:62`
- `vcs/vcs.py:29`

## 先说结论

### 结论 1：Sibling import 不是好设计，但它在当前仓库里是“有价值的坏设计”

它的问题是真实的：

- 修改 `sys.path`
- 引入解释器级全局副作用
- 增加运行上下文敏感性
- 更容易出现命名冲突和难定位问题

但它之所以还存在，是因为它解决了一个这个仓库必须面对的问题：

- 模块既要能单独复制使用
- 又希望多个模块一起复制时能自动协作增强

也就是说，它不是“无意义历史包袱”，而是“产品目标逼出来的折中方案”。

### 结论 2：第一轮先统一，不先删除，是因为“模式本身的代价”和“模式写法不统一”是两类不同问题

目前存在两个层次的问题：

#### 第一层：模式本身有架构代价

也就是：

- `sys.path` 改动不好
- import 行为太依赖运行上下文
- 模块边界不够干净

#### 第二层：这个模式在仓库里写得还不统一

也就是：

- 各模块的写法不同
- 命名风格不完全一致
- fallback 语义不够机械化
- 后续维护更容易继续发散

第一轮先解决第二层，因为：

- 风险低
- 不改行为
- 立刻降低维护噪音

而第一层要处理，必须重新审视产品体验、模块边界和分发方式，不适合第一刀就直接砍。

### 结论 3：当前 sibling import 不应该“一刀切”全部删除，而应该分类处理

按目前仓库情况看：

- `sse -> httpclient`：最有理由保留
- `config -> dotenv/yaml/jsonc`：有现实价值，但值得重新设计边界
- `vcs -> diff`：最值得重新评估，优先考虑弱化或改造

## 一、为什么 sibling import 会被认为“不好”

## 1. 它引入了解释器级全局副作用

当前模式的共同点是：

- 计算 sibling 目录
- 往 `sys.path` 前面插入路径
- 再执行 import

典型位置：

- `config/config.py:33`
- `sse/sse.py:62`
- `vcs/vcs.py:29`

问题在于，`sys.path` 不是模块私有状态，而是整个 Python 进程的全局导入搜索路径。

这意味着：

- 一个模块为了导入 sibling 改动路径
- 可能影响后续其他 import 的解析结果
- 问题往往不是立刻爆炸，而是运行上下文变化后才显现

这类问题最麻烦的地方在于：

- 难复现
- 难从表面定位
- 和导入顺序强相关

## 2. 它让模块边界从“显式依赖”变成“环境驱动依赖”

正常 package 设计里，依赖关系通常比较清晰：

- 要么安装了依赖
- 要么没安装
- 要么通过配置/注入显式传入

而 sibling import 的逻辑变成：

- 如果目录结构刚好存在
- 如果 `sys.path` 插入成功
- 如果名字没有冲突
- 如果 import 没出 AttributeError

那就启用增强能力。

这种能力发现方式很实用，但不够纯粹。

它的问题不是“能不能跑”，而是“依赖边界不够清晰”。

## 3. 它会放大名称冲突和上下文差异

例如：

- `yaml`
- `dotenv`
- `jsonc`
- `diff`
- `httpclient`

这些名字都不算特别强 namespace 隔离。

当用户运行环境复杂时，导入行为可能受这些因素影响：

- 当前工作目录
- 用户自己项目里的同名模块
- 先前别的代码是否修改过 `sys.path`
- 不同测试入口的导入顺序

所以 sibling import 的真正问题并不是“写法丑”，而是：

- 它让模块行为更依赖上下文，而不是只依赖显式 API

## 二、那为什么它还存在

答案很简单：因为它服务的是 `zerodep` 的核心产品承诺。

## 1. 这个仓库不是普通 package-first 项目

`zerodep` 的目标不是先做 package，再提供一个方便安装的库。

它的目标更接近：

- 在 monorepo 里维护
- 以单文件形式分发
- 允许用户“拿一个文件就走”
- 也允许用户“拿一组文件一起用”

这在 `plans/01-implementation-analysis-overview.md:1` 里已经讲得很清楚。

也就是说，这个项目天然需要同时满足两个要求：

- 单个模块尽量独立
- 多个模块组合时尽量自然增强

正常 package 方案里，这个问题很好解决，因为你可以依赖 package import 体系。

但在单文件复制模型下，这个问题没有那么好解决。

## 2. sibling import 解决的是“多文件复制后的自然协作”

如果用户：

- 只复制 `sse.py`
- 同时复制了 `httpclient.py`

那么从用户直觉出发，他会认为：

- 两个文件都在
- 那高层 SSE client 最好自动能用

如果这时完全取消 sibling import，通常会出现两种结果：

### 结果 A：能力直接消失

`sse` 只能保留 parser 层，不再自动接入 `httpclient`。

这会让多文件复制的体验下降。

### 结果 B：引入更强的显式依赖结构

例如：

- 要求 package 安装
- 要求用户手动注入 client
- 要求额外的初始化注册

这会让单文件复制体验变差。

所以 sibling import 不是“为了偷懒”，而是在当前产品目标下，用最小外部负担达成组合能力的一种折中实现。

## 三、为什么第一轮不直接删除，而只是统一

这其实是一个“重构顺序”问题。

## 1. 当前最容易改的是“写法不统一”

第一轮统一写法，解决的是这些问题：

- 各模块 import block 结构不同
- 命名风格不一致
- 后续 reviewer 每次都要重新理解

这类问题：

- 容易改
- 不改变产品行为
- 风险低
- 立刻有维护收益

所以像这次把 `config`、`sse`、`vcs` 都统一成 `_ensure_sibling_path(name)` 风格，是典型的第一阶段治理动作。

## 2. 删除 sibling import 会直接影响产品行为

一旦删除，不是“内部重构而已”，而是会影响这些用户体验：

- 复制多个模块后是否还能自动协作
- 高层功能是不是需要额外配置
- 某些增强能力是否直接消失

这种改动已经不是“代码整理”，而是“产品语义调整”。

因此必须在第二阶段或更后阶段处理，而不能在第一轮低风险规范化里顺手砍掉。

## 3. 先统一，才能更好地分类去留

如果当前每个模块的 sibling import 写法都不同，那么你很难准确回答：

- 这个模式到底值不值得保留
- 哪些地方是能力发现，哪些地方其实是隐式硬依赖
- 哪些 fallback 只是为了体验，哪些 fallback 是为了维持模块边界

先把 pattern 收敛成统一形态，后面再做 keep/remove 判断，成本会更低。

## 四、现有 sibling import 应该怎么分类

## A. `sse -> httpclient`：最有理由保留

位置：

- `sse/sse.py:62`

### 为什么保留价值高

`sse` 自身已经明确分成三层：

1. parser 层
2. high-level client 层
3. convenience API 层

这一点在 `sse/sse.py:1` 的模块文档里就写得很清楚。

这意味着：

- 低层 parser 本来就可以独立工作
- 高层 client 本来就依赖 HTTP streaming

在这种结构下，让 `sse` 自动接入 sibling `httpclient`，是很合理的产品设计。

因为它不是在偷偷依赖 unrelated module，而是在接入本模块高层能力所必需的 transport 层。

### 如果去掉会怎样

要么：

- 高层 API 失效，只剩 parser 还方便

要么：

- 必须改成显式注入 transport/client

后者并不是不行，但它会让当前的“复制后即用”体验明显变差。

### 判断

- 当前应保留
- 但未来可以考虑改造成“更显式的 transport 注入接口 + 保留默认 sibling fallback”

也就是说：

- fallback 可留
- 但应该逐渐从“唯一接入方式”变成“默认接入方式”

## B. `config -> dotenv/yaml/jsonc`：有价值，但值得重新设计边界

位置：

- `config/config.py:33`

### 为什么它有现实价值

`config` 的职责是统一配置加载。

而它要支持的来源包括：

- `.env`
- YAML
- JSONC
- TOML
- INI

其中 `.env`、YAML、JSONC 这几类格式刚好在仓库里都有对应模块。

让 `config` 自动利用这些 sibling 模块，从功能直觉上完全说得通。

### 但为什么它比 `sse -> httpclient` 更值得重新评估

因为这里并不是“一个高层功能自然依赖一个底层 transport”，而是“配置模块在动态拼接多个文件格式能力”。

这类依赖的问题在于：

- 能力面更广
- fallback 组合更多
- 导入块更多
- 模块边界更容易发散

而且 `config` 本身已经承担了：

- source precedence
- cast
- file loading
- flatten / nested lookup

再叠加多个 sibling format parser 后，内部复杂度和导入复杂度都会上升。

### 判断

- 当前不建议直接删除
- 但这是最适合未来做“能力注入化”或“显式 loader registry 化”的地方

可能方向：

- 保留默认 sibling fallback
- 但允许 `Config` 显式传入 loader map
- 或把某些格式能力做成更明确的可选钩子

这样会比当前完全由 import 决定能力边界更稳。

## C. `vcs -> diff`：最值得优先重审

位置：

- `vcs/vcs.py:29`

### 为什么这个关系最值得重审

`vcs` 的主路径价值在于：

- repo 检测
- status
- log
- blame
- branch/workspace 操作
- shell out 到 git/hg/jj

而 `diff` 更像是增强能力。

这意味着：

- `vcs` 的核心存在价值并不依赖 `diff`
- `diff` 的加入更多是“有了更好，没有也能工作”

与 `sse -> httpclient` 相比，这种关系没那么“基础能力必需”。

### 可能的重构方向

`vcs` 更适合未来改成：

- 没有 `diff` 时，保留纯 CLI wrapper 核心
- 有 `diff` 时，通过更显式的 hook / adapter / helper 接入 merge 能力

也就是说：

- 这里最有可能率先从 sibling import 走向更显式的扩展机制

### 判断

- 当前不需要立即砍
- 但在三者里，它最值得优先重新设计

## 五、如果真要逐步减少 sibling import，有哪些替代路线

## 方案 1：显式能力注入

### 例子

- `sse` 接收一个 transport function 或 client object
- `config` 接收额外的 loader map
- `vcs` 接收 merge helper

### 优点

- 依赖边界清晰
- 不再依赖 `sys.path`
- 更容易测试

### 缺点

- 使用门槛提高
- “复制多个文件即可自然协同”的体验下降
- 对当前仓库用户心智不够友好

### 适用度

- 对 `vcs` 很适合
- 对 `config` 中等适合
- 对 `sse` 可以作为高级接口保留，但不太适合直接替换默认体验

## 方案 2：保留默认 sibling fallback，但增加显式注入接口

这是我认为最符合 `zerodep` 哲学的中间方案。

### 做法

- 默认行为不变：有 sibling 就自动增强
- 同时提供显式注入方式给高级用户或复杂环境

### 优点

- 不破坏当前体验
- 给更干净的依赖路径留出口
- 后续可以逐步把 fallback 从“唯一接入方式”降级为“默认接入方式”

### 缺点

- API 面会稍微变宽
- 文档要求更高

### 适用度

- 对 `sse` 非常适合
- 对 `config` 也很适合
- 对 `vcs` 适合作为过渡方案

## 方案 3：正式 package 化依赖边界

### 做法

不再依赖复制目录结构，而是通过正式 package import 管理模块关系。

### 优点

- 边界最干净
- 导入最稳定
- 最符合传统库设计

### 缺点

- 直接削弱 `zerodep` 的核心卖点
- 用户不能再轻松复制单文件就用

### 适用度

- 对当前仓库整体不适合

## 方案 4：彻底拆分“核心能力”和“增强能力”

### 做法

例如：

- `sse` 只保留 parser
- 高层 HTTP SSE client 变成另一个文件
- `config` 的高级格式支持拆到外部适配层

### 优点
n
- 模块边界会更干净
- 核心模块可独立性更强

### 缺点

- 用户需要理解更多文件角色
- 模块数会变多
- 和当前“单文件就尽量完整”的产品风格有冲突

### 适用度

- 只适合极少数复杂模块，不适合大面积推进

## 六、推荐路线

基于 `plans/02-refactor-roadmap.md:1` 和 `plans/03-pattern-inventory.md:1`，我建议 sibling import 的策略分三步走。

## 第一步：统一写法

这一步已经开始：

- 统一 sibling path helper
- 统一 `_HAS_*` 能力标记风格
- 统一 import block 结构

目标：

- 降低维护噪音
- 不改行为

## 第二步：分类去留

建议当前分类如下：

### 保留为主

- `sse -> httpclient`

### 保留但逐步增强显式能力注入

- `config -> dotenv/yaml/jsonc`

### 优先评估弱化或替换

- `vcs -> diff`

## 第三步：让 sibling import 从“隐式唯一方案”变成“默认增强方案”

这是最重要的方向。

目标不是一刀切删除，而是逐步把它降级成：

- 默认方便行为
- 但不是唯一依赖接入方式

这会让仓库同时兼顾：

- 复制即用体验
- 更干净的依赖边界
- 更高的长期可维护性

## 七、最终结论

### 1. 为什么不直接删

因为删除 sibling import 不是简单重构，而是会改变产品语义和使用体验。

### 2. 为什么先统一 helper

因为当前最容易低风险改善的是“模式写法不统一”，而不是“模式本身是否存在”。

### 3. 哪些该保留

- `sse -> httpclient` 最该保留

### 4. 哪些该重审

- `vcs -> diff` 最该优先重审
- `config -> dotenv/yaml/jsonc` 应逐步转向更显式的能力边界

### 5. 最合理的长期方向

不是“全部删光”，也不是“继续任其扩散”，而是：

- 先统一
- 再分类
- 最后把它从“隐式硬依赖发现机制”演进成“默认增强机制”

这才是最符合 `zerodep` 单文件哲学的演进路线。
